## Findings

### I1 — The isolated CLI has no defined source-manifest input at its required path

**Important; open.** P:206 creates the independently authored manifest only at `zig/tools/ui_atlas/fixtures/atlas-inputs-v2.json` and explicitly postpones installation at `assets/ui/atlas-inputs-v2.json` until Task 11. P:248 defines `inputs.read(ctx, fs, root, identity)` with no manifest argument or alternate resolution contract. P:329 requires an explicit root but exposes no manifest override. The actual Task 9 build/harness commands use `--root .` in the canonical repository (P:332–339), while Tasks 1–10 cannot modify existing assets/integration paths (P:17).

S:94 requires the separately reviewed source authority, and S:164 requires authenticated input buffers for generation. Pure Task 6 can pass fixture bytes directly in `SourceSet`; the full CLI in Task 9 cannot do so through its declared interface. As written, a compliant implementer must either wait for Task 11, invent an undocumented fixture fallback in production input admission, or cross the asset ownership boundary early. None is the specified task order.

**Required correction:** define the isolated end-to-end root before Task 9. For example, have the harness materialize an invocation-owned repository-shaped root under ignored output, containing the reviewed source manifest at the canonical relative path, the exact allowlisted source assets, and the authenticated source closure; build and invoke against that root. Specify which task creates it, validates its exact bytes, and cleans only owned data. Alternatively define a reviewed explicit source-authority selection API with its authentication and identity rules. Update the actual commands accordingly. Preserve identical source-manifest bytes and semantic paths at the Task 11 owner installation; do not silently teach normal release admission to fall back to a test fixture.

### I2 — Qualification admission cannot distinguish required target rows

**Important; open.** P:368 declares `qualify.Row` as `{kind, artifact, profile, status, evidence_hash}` and `qualify.admit(rows, expected)` as rejecting absent/duplicate/mismatched required rows. The only identity dimension for a generation or runtime row is its broad `kind`; `evidence_hash` is an opaque digest, and `admit` receives neither witness bytes nor a resolver. P:379 requires three actual generation hosts, and P:381 requires several graphics backends, viewports, scales and other runtime cases. S:243–248 requires those distinct hosts/backend/scale rows, and S:170 requires validation of the complete witness closure.

Deduplicating by kind prevents multiple legitimate runtime/host rows; deduplicating by the complete current record or evidence hash permits several differently hashed reports from the same host to stand in for the missing targets. Counting rows cannot establish which required targets they cover. The sentence deferring witness schema to the platform design (P:368) does not supply a producer/consumer bridge from that schema into the declared `Row`/`admit` API. Task 8's `release.validate` does receive witness bytes (P:276), so the plan currently has a stronger release validator and an under-specified qualification admission surface.

The existing platform implementation plan already supplies the necessary vocabulary: `docs/superpowers/plans/2026-10-09-nyon-zig-platform-bindings.md:118–125` defines `Requirement{id,target,environment,stage,test_spec}` and `Witness{requirement_id,candidate_id,asset,shader,host,environment,fixtures,evidence,target,stage,status,exit_code}`. Its line 138 requires the environment digest to resolve to exact OS/browser/GPU/driver/backend/scale metadata and specifies arena ownership for `OwnedWitness`. Reuse that contract through an explicit validated adapter; this finding does not request a new competing witness schema.

**Required correction:** freeze the row key and required-set producer, including the relevant host/backend/case/scale identity, or make `admit` consume validated witness objects whose constructor parses and authenticates those fields and evidence bytes. Define the bridge from Task 8 release validation to Task 11 aggregation so these two gates use the same required set. Add negative cases for repeated macOS generation evidence replacing Linux/Windows, repeated Metal cases replacing another backend, wrong candidate/profile, duplicate case keys, and missing/unverified rows. Evidence hashes alone are insufficient input for these checks.

### I3 — Task 11's prescribed RED exercises the already completed font task

**Important; open.** P:370–375 correctly proposes a compiling success stub for `qualify.admit` and the behavioral test `atlas qualification refuses missing target evidence`. Its next mandatory RED instruction, P:378, instead names `atlas ttf trailing hmtx and bounded cmap` and repeats Task 2's entire parser checklist from P:130. By Task 11, the named font test is already GREEN under the dependency/review protocol in P:46 and P:402. Running that filter cannot demonstrate the new qualification stub fails, and completing that checklist supplies no missing-target admission evidence.

**Required correction:** replace the copied bullet with the qualification test's exact filter and the Task 11 admission negative matrix, including I2's required-set cases. Require an observed assertion mismatch against the compiling success stub, nonzero matched test count, and actual exit before implementation. Keep the parser tests in Task 2 and the full-suite regression run in the shared protocol.

## Preserved design constraints and evidence boundary

The plan correctly retains all four original design-review corrections: ordered file/directory/parent barriers, running-image/compiled-source binding, fixed numerical operation order, and artifact-relative hash paths. It also preserves the fix-2 separation of successful candidate publication from selection commitment. P:294–306 reproduces all eleven normative focused outcome rows from S:213–223 with the correct candidate-versus-selection uncertainty exits. Promotion failures before selection replacement stay `NotCommitted`; candidate uncertainty never implies a selection write. Existing-candidate re-sync, deferred cancellation, ownership-preserving cleanup and read-only checks are explicit.

Bounds are substantially specified before implementation: font/table/glyph/contour/component/instruction limits, SVG token/operand/element/subpath limits, flattening caps, bounded snapshots/receipts and the 64 MiB accounted context (P:19,86,264; S:96). No plan text permits truncated geometry or production checksum bypass. Independent arithmetic and primitive fixtures precede generated product evidence. Source closure includes the adapter/template/profile/build/pin; actual executable authentication and forged/stale/raced receipt tests are required. Those are proposed protocols, not current proofs of their implementation.

**Unverified prerequisites, not plan defects:** actual per-host compiler distribution provenance, implemented source closure and executable authentication, macOS/Linux filesystem flush/replacement/power-loss semantics, Windows publication capability, actual cross-host identical generation and performance, all native/browser renderer/retained-screen/accessibility rows, and a Rust-free delivered build/link/package graph. P:23,268,339,379–396 correctly refuses to turn model tests, compilation or screenshots alone into those passes. Missing hardware may leave a valid implementation at candidate qualification; it does not authorize release promotion or Rust retirement. The three findings above are resolvable plan defects independent of access to that hardware.
