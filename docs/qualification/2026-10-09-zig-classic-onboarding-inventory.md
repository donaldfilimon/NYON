## Current Rust onboarding contract

Exact enum/order and observation mapping (`src/app/onboarding.rs:4-21`, `:36-43`, `:79-85`):

| Index / progress | Step | Matching event |
| --- | --- | --- |
| 0 / 1 of 6 | `SelectUnionWorld` | `UnionWorldSelected` |
| 1 / 2 of 6 | `PreviewLaunch` | `LaunchPreviewed` |
| 2 / 3 of 6 | `LaunchFleet` | `FleetLaunched` |
| 3 / 4 of 6 | `TuneField` | `FieldTuned` |
| 4 / 5 of 6 | `ReadAdvisory` | `AdvisoryRead` |
| 5 / 6 of 6 | `OpenScenarioEditor` | `ScenarioEditorOpened` |

`new(false)` starts index 0; `new(true)` is inactive. Active means an optional index exists. Progress is index+1 while active and 6/6 when inactive. Unexpected events leave state unchanged. `observe` returns true **only** for the transition from the last matching event to inactive, not for ordinary progress; further observations return false. `skip` makes inactive and returns whether it was active; `reset` always returns to index 0 (`src/app/onboarding.rs:51-109`). No partial progress is durable: preferences store only `onboarding_completed` (`src/preferences/mod.rs:53-59`). A replay of guidance is reset, not a replay/reconstruction of authority.

Startup loads preferences once, records its recoverable message, derives onboarding from completion, selects Paused for active guidance or Normal otherwise, and initializes remembered resume speed to Normal (`src/app/core.rs:192-202`, `:218-230`, `:235-238`). A nonpaused speed request during active onboarding is refused before changing speed/resume/clock. Same-speed requests also return before clearing residue; a changed nonpaused speed updates resume speed and clears clock (`src/app/core.rs:271-282`). Settings/editor holds preserve selected speed and clear clock during advance (`src/app/core.rs:790-802`).

Observations are tied to specific immediate operations, not to a frame-wide scan:

| Event | Current trigger and guard |
| --- | --- |
| Union selection | Mouse/touch scene tap on a Union-owned target observes after updating selection; touch friendly selection returns immediately. Generic `select_scene_world` clears focus/target but does **not** observe. Guidance-button selection additionally requires Playing, exact first step and Union ownership (`src/app/core.rs:400-407`, `:698-740`; `src/app/core/session.rs:25-36`). |
| Launch preview | `set_scene_cursor` rejects nonfinite cursor, updates hover only in Playing, then observes only if contextual preview exists and succeeds; touch destination selection does the same validity check. Simple `hover_scene_world` alone has no observation (`src/app/core.rs:410-413`, `:678-691`, `:717-728`). |
| Launch/tune | Playing queue dispatch captures immutable preview validity, enqueues, then consumes sequence; only successful enqueue with valid preview observes Launch/Tune. A gameplay-invalid preview can still enqueue without an observation. Launch clears touch target only in its preview-valid branch (`src/app/core.rs:767-787`). |
| Advisory read | Explicit `UiAction::AcknowledgeAdvisory` observes and returns true; this branch has no additional mode, freshness, publication or score guard. The automaton supplies the step guard (`src/app/core/session.rs:50-53`; `src/app/onboarding.rs:78-89`). Do not add a GPU-success gate to 3E. |
| Editor opened | `handle_action(Action::Scenario)` first requires Playing, then observes **before** calling `open_editor`. Direct `open_editor` does not observe; it creates detached editor, focuses first editor widget, enters EditingScenario and clears clock (`src/app/core.rs:606-609`, `:630-633`, `:821-831`). |

Completion updates live completion flag, resumes remembered speed if selected speed is Paused, then persists preferences. Skip performs the same actions only when it was active; already-inactive skip emits no save. Neither path replaces simulation, clears selection or drains queued intent (`src/app/core.rs:985-991`; `src/app/core/session.rs:176-183`). The existing onboarding journey queues Launch/Tune while tick remains zero and completion enters the held editor, so guidance is explicitly not tick acceptance (`tests/usability.rs:93-126`).

**Two reset paths must remain distinct.** HUD/public `reset_onboarding` resets progress/completion, clears help, requests Paused and persists. Settings `ResetOnboarding` resets progress/completion and pauses, then applies/persists preferences through the common settings path; it does **not** clear help or close Settings. Neither explicitly clears HUD focus, selection or queue (`src/app/core/session.rs:148-173`, `:186-191`). Do not route Settings reset through public reset and accidentally change help behavior.

Restart/confirmed apply reset selection/hover/touch target, field, speed to Paused if guidance remains active or Normal otherwise, resume speed to Normal, help, HUD focus, sequence, clock/camera/visual time; they do **not** reset onboarding progress or preferences. Editor cancellation returns Playing and clears clock/general recovery message. Completing the final step before opening editor may resume speed, but mode then holds ticks until editor close (`src/app/core.rs:904-920`, `:959-991`; `src/app/core/session.rs:176-191`). Campaign finish does not complete/reset onboarding automatically: tick-report handling only schedules advisory, and explicit onboarding branches alone set the completion flag (`src/app/core.rs:805-818`, `:985-991`).

## Current preferences and failure behavior

Preferences default to 100% scale, Full motion, false contrast, Auto quality and incomplete onboarding; supported scale values are exactly 85/100/115/130. Presentation projection contains motion/contrast/quality, not scale/completion (`src/preferences/mod.rs:15-47`, `:53-79`). Task 1 already has these values and projection in Zig (`zig/src/preferences.zig:9-62`).

Load is automatic at session creation. Absent slot means defaults without failure; successful decode supplies stored preferences; store/codec failure means defaults plus a recoverable failure. Load does not call save or repair corrupt/missing data (`src/preferences/mod.rs:145-153`; `src/app/core.rs:194-202`). Native/browser legacy fallback reads only when primary is absent; primary presence or load error wins. Writes target current slot, with native atomic persist and browser current-key write (`src/scenario/store.rs:22-29`; `src/preferences/store.rs:177-205`, `:210-223`, `:247-284`). No copy-on-read migration is required.

User setting actions require Settings. Every accepted non-Close action updates live preferences, applies presentation/camera motion, then saves immediately, including setting an already-selected value; Close only closes and returns. There is no separate Save Settings button and no deferred frame autosave. Completion/skip/reset also automatically save as a consequence of their explicit action or observation; intermediate steps do not save (`src/app/core/session.rs:148-191`; `src/app/core.rs:985-1002`).

`save_or_default` returns default preferences on encode/store failure, but AppCore consumes **only its recoverable message**, so successful in-memory changes stay usable. Never assign a failed save's `outcome.preferences` back into the live core. A later successful save replaces the preference message with None; a general recoverable message takes display precedence without deleting the preference message (`src/preferences/mod.rs:156-167`; `src/app/core.rs:581-584`, `:995-1002`). `set_presentation_preferences` is a separate transient projection seam; it changes presentation/camera directly, not the durable preference record (`src/app/core.rs:368-374`).

Task 2 Zig `loadOrDefault`/`saveOrDefault` already implement typed preference outcomes, including default preference value on failure; owned StoreFailure must be deinitialized and optional rendered message belongs to caller. `loadOrDefault` frees loaded payload; `saveOrDefault` frees encoded payload. Allocator failures propagate as `error.OutOfMemory`, not as a recoverable store/codec-default outcome (`zig/src/classic_store.zig:626-688`). Task 3E should consume these outcomes, not add another store/codec. For OOM in load/save/message rendering, Proposed composition must retain typed failure visibility and preserve live state rather than report success or lose a prior error because message allocation failed. The allocation test already requires zero save calls and unchanged sentinel bytes on encode OOM (`zig/src/classic_store_tests.zig:695-709`).

## Ordered actions and real focus ownership

Current Classic focus belongs to AppCore's `ui_focus_action: Option<UiAction>` and SettingsState's bounded index, not the host's shared `FocusManager` (`src/app/core.rs:166-168`; `src/app/settings.rs:18-40`). Editor owns its independent widget focus (`src/app/core.rs:825-829`). The guide swaps/restores host `ui_focus`, clears interaction/key edges and resets host frame baseline; Classic HUD identity remains in AppCore (`src/app.rs:1637-1664`).

The typed UiAction enum includes payload-bearing guidance-world, field and Settings actions; do not replace equality with ordinal position or untyped string matching (`src/presentation/ui.rs:24-41`). Current Playing order is:

1. SpeedDown, TogglePause, SpeedUp, Launch, ClearSelection, ResetCamera, OpenSettings, ToggleHelp, OpenScenario.
2. SkipOnboarding if active.
3. SelectField(Atmosphere), SelectField(Hydrosphere), SelectField(Topology).
4. DecreaseField, IncreaseField, AcknowledgeAdvisory.
5. ResetOnboarding if help visible.
6. AppCore appends SelectGuidanceWorld(world) if Playing and the start-marker projection exists.

This order is literal source order, independent of geometry; first three speed controls are disabled during onboarding, Launch follows tray enabled state, ClearSelection follows source/destination presence, field +/- follow their preview controls, advisory/read/help reset remain enabled (`src/presentation/ui.rs:470-550`, `:593-685`; `src/app/core.rs:498-520`). Proposed 3E can define typed action/enablement descriptors with the optional marker action supplied by 3H/3G; it must not invent marker placement or choose a marker without those owners.

Settings order has exactly 11 enabled controls: Scale85, Scale100, Scale115, Scale130, SetMotion(opposite current), SetHighContrast(opposite current), QualityAuto, QualityLow, QualityHigh, ResetOnboarding, Close (`src/presentation/ui.rs:703-779`). Motion/contrast payloads are recomputed from live preferences; Settings retains an index so toggling the payload keeps focus in the same control. Focus clamps to 10 and wraps modulo 11 (`src/app/settings.rs:24-39`).

Playing HUD focus stores whole typed action equality. Frame construction looks up that identity to mark focus; getter resolves its current index. Navigation traverses **all** controls, including disabled controls. Empty frame clears focus; if stored action is missing, forward starts at first and backward at last. Invalid index focus request leaves prior identity unchanged. Activation finds same identity **and enabled**; missing/disabled activation clears HUD focus and returns false. Settings disabled activation returns false without a focus reset (`src/app/core.rs:305-314`, `:535-549`; `src/app/core/session.rs:79-145`). Frame rebuild alone neither retargets nor eagerly clears a vanished identity. Proposed `focusIndex(ordered_controls)` should remain pure; clear only at explicit source transition/failed activation.

Explicit focus reset sites are: open Settings resets settings index and clears HUD identity; scene selection/tap and clear-selection clear HUD identity; restart/apply clear HUD identity. `clear_ui_focus` itself only operates in Playing; close Settings does not explicitly clear settings index/HUD identity, and open editor does not explicitly clear HUD identity (`src/app/core/session.rs:6-20`, `:73-76`; `src/app/core.rs:400-407`, `:659-664`, `:698-703`, `:821-831`, `:966-982`). Thus Proposed typed focus-reset effects must distinguish HUD clear, settings focus default, and editor/guide ownership, not a global clear-all.

3H owns bounds/hit/culling/render/semantics and marker/guide geometry; 3I owns event priority, gestures, edge consumption, guide holds and host-independent routing (`docs/qualification/2026-10-09-zig-classic-app-inventory.md:364-410`). Current routing resolves pointer focus at contact begin, requires enabled control, consumes opaque HUD, clears HUD focus for world/empty scene before gesture dispatch. Settings arrows/Tab navigate its index; Escape closes. Editor text, including spaces, wins before activation; Playing Enter/Space activates when a current HUD focus index resolves, otherwise normal gameplay binding runs. Host HELP interception opens guide rather than direct AppCore help toggle (`src/app/input_router.rs:156-180`, `:431-462`, `:625-698`, `:251-263`). Preserve those boundaries in 3E's values; implement raw routing later.

## Current Zig seams and Proposed consumption

3A AppCore already receives preference values at init, derives speed/hold, owns preference record and exposes `setPreferences`, `setOnboardingHold`, `setMode`, speed/resume projections. Hold release resumes remembered speed and clears residue; hold does not set completion flag. Replacement preserves preference record and hold but resets selected/resume speed, selection/help/sequence (`zig/src/classic_app.zig:93-123`, `:174-214`, `:278-302`). There is currently no Zig onboarding automaton or Classic HUD/settings focus field in this core. Compose them in the Proposed session owner instead of hiding progress in the hold boolean (`zig/src/classic_app.zig:93-110`).

3B's `Effects { clear_ui_focus, observation }` and Interaction/Dispatch are values. Its four observations cover selection/preview/launch/tune; generic selection only clears focus, cursor hover may observe preview, primary tap may observe selection/preview, successful valid-preview enqueue observes launch/tune. Dispatch errors return before effects. Plain command tray/preview is read-only and emits no observation (`zig/src/classic_commands.zig:7-9`, `:31-77`, `:91-109`, `:132-145`).

Proposed sequence for each successful 3B operation: apply its HUD-clear effect, map its optional observation to the six-event automaton, synchronize hold/completion on an actual final transition, emit save intent only for completion. Add explicit advisory-read/editor-open observations in session action dispatch. Do this before returning to caller or opening editor, matching Rust immediate order. Do not deduce success from `handled`, from a read-only tray being valid, or from `FrameOutcome.accepted_commands`. Rust observation dispatch and tick acceptance are separate (`src/app/core.rs:767-818`; `zig/src/classic_app.zig:164-172`, `:258-267`).

Host cursor events currently invoke preview observation on cursor movement; redraw instead drains semantic actions, computes delta and runs runtime update, holding guide time with zero delta (`src/app.rs:2277-2287`, `:1856-1878`). 3E must not poll current selection/preview every frame: doing so could advance a newly reset instruction from old state without the matching source action. `advance` itself only handles visual/clock/report work (`src/app/core.rs:790-818`).

Proposed modules/value seams:

- `classic_onboarding.zig`: six Steps/Observations; optional index; `init/active/step/progress/observe/skip/reset`. Return explicit progress/completion transition or preserve Rust completion-bool contract; never infer completion from mere step change.
- `classic_settings.zig`: six SettingsAction variants with typed values; exact 11-control ordering/projection and clamped/wrapped index. No geometry, storage or authority.
- `classic_session.zig`: externally composed AppCore reference/ownership plus automaton, settings index, typed HUD identity, preference failure status. Pure transition methods return ordered effects such as preferences-changed, presentation-changed, persist-current-preferences, editor-open request and HUD-focus-clear. Store-independent reducers allow behavioral tests without native profiles. A narrow adapter consumes Task 2 outcomes and retains/frees owned failures/messages. Successful restart/apply notification clears session HUD focus **after** core replacement succeeds; failed installation preserves focus/session state.
- Avoid duplicate preference records drifting between session/core. Choose one authoritative live value (existing AppCore preferences) and update through `setPreferences`; derive onboarding hold from automaton at explicit transitions. Read-only projection supplies typed ordered controls to 3H, then 3I dispatches typed actions back. Shared exports/build/gate edits remain parent integration responsibility (`docs/qualification/2026-10-09-zig-classic-app-inventory.md:202-207`).

These APIs are Proposed, not Current implementation. In particular effect ordering, typed OOM presentation fallback and post-install notification need review before implementation.

## Proposed independent behavioral and failure expectations

Use literal expected steps/order/flags and before/after authority/queue/slot witnesses, not expectations computed by the controller under test. Existing assertions are source oracles only.

1. Table-drive exact six-event progression; each unexpected event leaves step/progress unchanged, only final event returns completion, inactive observations/skip are inert, reset reports 1/6. Expected sequence is independently literal (`src/app/onboarding.rs:117-133`).
2. First-run hold rejects speed changes, long elapsed time produces zero ticks, touch source/destination advances exactly two steps with zero queued commands; launch/tune advances while authority stays tick zero, advisory then editor completes, editor keeps zero ticks. Port the existing journey's explicit checks (`tests/usability.rs:93-126`). 3. Skip and completion preserve scenario/digest/queued commands/sequence/selection; resume Normal at startup or previously remembered Fast/VeryFast after reset. Inactive skip performs zero saves. 4. Distinct settings/public reset: both restart guidance/clear completion/pause/persist, Settings reset stays Settings and retains help; public reset clears help. Neither clears queue.
